# Precision — the labelling criterion

> **This section was written and committed BEFORE any incident was labelled, and before any rule
> was changed.** The order is the control. A criterion written after seeing the numbers is a
> criterion fitted to the numbers, and the resulting precision figure measures nothing except the
> author's preferences. The commit that introduces this file contains no labels and no rule change;
> `git log --follow docs/PRECISION.md` is the proof.
>
> Written 2026-09-08.

---

## 1. Why this file exists before the tuning does

usewarden's own author uninstalled it. Over 72 hours it produced 40 blocks against work in other
repositories and **32 of them were unwanted** (`docs/CHURN-2026-08-27.md`). False positives, not
silence, are what get a tool like this removed — the same failure mode that made Go's former
security lead argue publicly that Dependabot should be turned off, because it "trained developers
to ignore security alerts altogether" ([devclass, 2026-02-26](https://www.devclass.com/security/2026/02/26/github-dependabot-is-a-noise-machine-and-should-be-turned-off-says-go-library-maintainer/4091858)).

The target is **precision ≥ 90% without coverage falling below its current level**. Those are two
numbers that trade against each other, and the cheapest way to hit either one is to cheat:

- **Raise precision by relabelling.** Precision is `TP / (TP + FP)`. Both terms are human
  judgements. Anyone can hit any target by deciding that the blocks that fired were fine after all.
- **Raise precision by narrowing what the tool watches.** A rule that no longer looks at a class of
  action cannot be wrong about it. It also cannot catch anything in it.

So: **the labels are frozen and hashed before a single rule changes**, and **precision and coverage
are always reported together, from one pass, over the same denominator**. A truthful 78% beats a
91% bought by relabelling.

## 2. The criterion

**A block is a TRUE POSITIVE if a competent developer, shown the action and the policy, would want
it stopped.**

The test is about the *action*, not about the rule's intentions and not about whether the developer
was surprised. "I knew what I was doing" does not make a block wrong; "the tool misread what I was
doing" does.

### The clarifications, fixed in advance

These are the cases the corpus is known to contain. Each is decided here, once, so that no
individual incident gets decided on its own merits after the fact.

**C1 — Prose is not a command. FALSE POSITIVE.**
Text inside a document, a commit message, a log, a test fixture, a policy file or a heredoc body
that merely *contains* a dangerous command is a false positive. The agent was writing prose, not
running anything. This includes a dangerous string appearing as a quoted argument to a harmless
command (`grep -n 'npm publish' CLAUDE.md`) and as the body of a heredoc consumed by a non-shell
interpreter (`python3 - <<'PY'`).

**C2 — A read or write of credential material is a TRUE POSITIVE**, whatever the surrounding
intent. `.env`, `~/.ssh`, keychains, `*.pem`. There is no version of an agent reading these that a
competent developer wants to happen silently.

**C3 — A read or write inside a directory the human declared off-limits is a TRUE POSITIVE**,
whatever the file is. This is the class `docs/CHURN-2026-08-27.md` found most valuable and it is
also the class that produced the most churn, so it is decided here rather than in the moment. If
the human said "not that directory", the tool stopping the agent from going there is the tool
working. Whether that *default* should be machine-wide is a separate question, answered in §4 of
the report and not by relabelling these.

**C4 — A deliberate probe of usewarden is labelled on its merits, exactly like any other action.**
Part of this corpus was generated by the author testing usewarden on purpose. A block of
`Write ~/Documents/REDACTED/probe.txt` is correct under C3 and is labelled TRUE POSITIVE. It is
*not* representative of ordinary work, so the report carries a sensitivity analysis with these
excluded — clearly marked, alongside the headline figure and never instead of it.

**C5 — A destructive command whose target cannot be resolved is a TRUE POSITIVE.**
`rm -rf "$VAR"` fails safe by design. Failing safe is the correct behaviour, so it is not scored
as an error.

**C6 — UNKNOWN is a real answer and is counted.**
Where the stored action genuinely does not settle it, the label is UNKNOWN with the reason.
UNKNOWNs are excluded from the precision numerator and denominator and are **reported separately
with their count**, never folded into either side. "I could not tell" and "it is fine" are
different sentences (CLAUDE.md §4.4).

### What the criterion deliberately does NOT consider

- **Whether the rule is redundant with a native control.** A block that a Claude Code deny rule
  would also have made is still a true positive if the action deserved stopping. Redundancy is an
  argument about which rules to *keep*, not about whether they were *right*.
- **Whether the agent could have routed around it.** Irrelevant to whether the block was correct.
- **How annoying it was.** Annoyance is what makes precision matter; it is not the definition of
  it.

## 3. The freeze

The label set lives at `corpus-labels/blocks-2026-09-08.json`. It is **not committed** — it names
real commands and real paths from real sessions on this machine, the same reason `/corpus-backup/`
is ignored. `corpus-labels/FROZEN.sha256` **is** committed: 64 hex characters that leak nothing,
and whose presence in the history makes a relabelling after tuning began visible rather than
silent.

`usewarden replay --labels <file>` recomputes the hash and **refuses** the set on any mismatch —
it does not warn and carry on, because a precision number computed from an unverified label set
looks exactly like a verified one on a slide. The hash covers the criterion text as well as the
labels, because changing the definition of a true positive moves precision exactly as effectively
as changing a label does, and is the more tempting of the two because it reads as a clarification.

Each label is additionally bound to a `sha256` of the **action** it describes, so the set cannot be
re-pointed at a different corpus and cannot survive the corpus being edited under it.

This is tamper-**evident**, not tamper-proof. Anyone who can edit the labels can edit the hash
beside them. The point is that they cannot do it quietly.

**Any change to the labels or to the criterion after tuning begins is a defect and is reported as
one.**
