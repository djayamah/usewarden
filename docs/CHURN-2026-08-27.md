# The churn event: user number one uninstalled the product

**Diagnosis only.** Nothing is fixed in this document and nothing should be fixed from it until
the labelling work in front of it is done. A fix designed while annoyed is how the labelling
criterion gets bent to fit the annoyance — see §7.

---

## 1. What happened, and when, measured rather than remembered

The author of usewarden ran `usewarden uninstall` on his own machine because usewarden was
obstructing his work on his other projects. He is the only person who has ever run this product
against real work for a sustained period. He stopped.

Three dates, because they are not the same date and the difference matters:

| What | When (UTC) | How it is known |
|---|---|---|
| Protection judged not worth keeping | 2026-08-27 | the founder's account; this document carries his date in its name |
| Last block against real work | 2026-08-29 05:24:05 | `incidents` table, live corpus |
| `uninstall` actually rewrote the configs | **2026-08-29 09:42:14** | mtime of all three agent config files, to the second |
| Last hook invocation of any kind | 2026-08-29 09:40:57 | `~/.usewarden/usewarden.log` |

Protection therefore ran for **two days after it had already lost the argument**, which is its own
small finding: the decision to stop using a tool and the act of removing it are separated by
however long it takes to get around to it, and every block in that gap is spent from an account
that is already overdrawn.

`verification/uninstall-proof-2026-08-29.txt` is the per-file proof that it is now off.

---

## 2. Method

Window: the 72 hours ending 2026-08-29 09:44 UTC. Population: every incident in the live corpus
whose session `cwd` was **outside** this repository — that is, every time usewarden interrupted
work on something other than itself.

**46 incidents: 40 Layer-1 blocks and 6 Layer-2 judge warnings.**

Grouped by class below, never by instance, because eleven separate refusals to write eleven
ordinary source files under one bad policy line are one defect, not eleven.

The question asked of each class is deliberately not "was the rule correctly applied". It was, in
all forty. The question is **would a competent developer have wanted this stopped** — which is the
only question that predicts whether they uninstall.

---

## 3. The forty blocks, by class

### Class A — the project the session was told to work in was on the forbidden list (17 blocks)

**Attempted:** ordinary work in the agent's own working repository — a migration, two library
modules, a deploy script, an engine module, a test, a screenshot, three shell scripts, two design
documents, a plan file. Reads, writes and edits alike.

**Rule:** `scope.forbidden_paths[12]`.

**Why it fired:** that repository was listed in `forbidden_paths` **and** in `allowed_paths` at the
same time. `forbidden_paths` is an absolute veto checked first (`src/engine/layer1.ts:80`), so the
allow entry was silently dead. Nothing warned that the two lists contradicted each other.

**Wanted stopped: 0 of 17.** Every one was the agent doing exactly the job it had been given, in
exactly the directory it had been given, and being told it could not.

**And the message told the user something false.** Every `forbidden_paths` refusal carries one
hard-coded sentence (`layer1.ts:86`):

> `Usewarden: PLAN.md is on the forbidden list (~/dev/<app>). Usewarden blocks all agent access to credentials and key material. Do not retry; ask the human if you genuinely need this value.`

`PLAN.md` is not a credential and does not hold a value. The sentence is written for `~/.ssh` and
is emitted for every entry in the list regardless of what that entry is. A user reading this
seventeen times does not conclude that their policy needs a line removing. They conclude the tool
does not know what it is looking at. The founder reached that conclusion in writing, in a session
goal on 2026-08-29: *"The block messages claim 'credential files', which is wrong and is itself a
bug."*

### Class B — one forbidden entry that swallowed an entire tree (3 blocks)

**Rule:** `scope.forbidden_paths[10]`, which was `~/Documents` — the macOS Documents folder,
containing several unrelated working repositories as well as the private material the entry was
written to protect.

**Wanted stopped: 2 of 3.** The two that landed on the private vault were correct. The one that
landed on a working repository that merely happened to live under `~/Documents` was not.

The entry has since been narrowed by hand to the two specific directories it meant. That narrowing
is the correct fix and the user had to discover it himself, mid-task, from block messages that told
him he had touched a credential.

### Class C — repositories genuinely declared off limits (3 blocks)

**Wanted stopped: 3 of 3.** Correct, and one of them is the single most valuable thing usewarden
did in this window — see §5.

### Class D — real credential paths (2 blocks)

An SSH private key and a `.env`. **Wanted stopped: 2 of 2.** This is the product working.

### Class E — usewarden locked the user out of usewarden (3 blocks)

**Attempted:** two writes to `~/.usewarden/usewarden.yaml`, and one write to the agent harness's
own per-session scratchpad directory under `/private/tmp/...`.

**Rule:** `scope.allowed_paths`.

**Wanted stopped: 0 of 3.** Two failure modes, both structural:

1. **The escape hatch is behind the lock.** The documented way to widen scope is to edit
   `usewarden.yaml`. That file is not inside `allowed_paths`, so the write to fix the policy is
   refused by the policy. The remedy exists — `usewarden allow`, human-only by design, which is
   correct — but the message does not name it. It says *"have the human widen scope in
   usewarden.yaml"*, which is advice to perform the action that has just been refused.
2. **The agent's own scratchpad is out of scope.** Every Claude Code session is given a private
   temp directory and told to use it instead of `/tmp`. usewarden has no exemption for it —
   `grep -rn 'tmpdir|/private/tmp|scratchpad' src/engine src/policy` returns nothing. This will
   fire for **every** user whose `allowed_paths` is their repository, which is the shipped default.
   It is a guaranteed false positive on a path the user never chose and cannot see.

### Class F — the recursive-delete rule, which stopped nine things and no deletions (9 blocks)

**Rule:** `commands.deny[0] (rm-rf-outside-repo)`.

| Shape | n | What it actually was |
|---|---|---|
| deleting the agent's own session scratchpad | 2 | temp directory the harness created for it |
| `rm -rf node_modules`, `rm -rf /tmp/stagetest` | 2 | the two most routine deletions in software |
| deleting the session's own regenerable build output | 2 | inside the project, immediately regenerated |
| **writing a shell script whose text contains `rm -rf`** | 2 | a heredoc and an in-place edit. No deletion |
| **`grep` whose search pattern contains `rm -rf`** | 1 | reading code to find the deletion path in it |

**Wanted stopped: 0 of 9.** The last three rows are not deletions at all. The final one is the
purest form of the defect: an agent auditing a file for dangerous operations was refused for
naming one in a search pattern.

### Class G — `DROP TABLE` inside a Python string literal (1 block)

A Python heredoc editing a source file, replacing a string that contained `DROP TABLE`. No SQL was
executed and none could have been. **Wanted stopped: 0 of 1.**

### Class H — the `.env` rule (2 blocks)

One genuinely sourced a `.env` file; the block is defensible even though the script was written to
print names and not values. One was a Python heredoc writing a comment block. **Wanted stopped:
1 of 2.**

## 5. The one that justifies the product, stated as plainly as the failures

On 2026-08-28 an unattended agent, working in one repository under instructions that said in
capital letters that a second repository must not be touched **even to read**, read a file in that
second repository. usewarden blocked it (`scope.forbidden_paths`, incident 76).

That is the catch nothing else on the machine makes. It is not duplicated by the agent's own
permission prompts, because the agent believed it was doing something reasonable. It is the
cross-repository case, and §6 of `docs/RETENTION.md` weighs what a project-scoped default would
cost it.

The Layer-2 judge deserves the same paragraph. Its six warnings in this window include an agent
operating in the wrong one of two identically-named sibling repositories — three times, correctly,
with the reasoning written out — and a session told to change nothing that had begun deleting
25.7 GB. **The judge warned and did not block, and it was right nearly every time.** The layer that
obstructs is the layer that was wrong; the layer that was right does not obstruct.

## 6. Which rules caused the churn, named

Ranked by blocks caused, unwanted only:

1. **`scope.forbidden_paths` — 21 unwanted blocks.** Three distinct defects compounding:
   - *No conflict detection.* A path in both lists loses silently (`layer1.ts:80`).
   - *One hard-coded message for every entry* (`layer1.ts:86`), asserting the target is a
     credential when it is usually a source file.
   - *Positional rule identity.* The rule id is `scope.forbidden_paths[12]`, an array index that
     shifts the moment the list is edited. Directly observed here: index `10` means `~/Documents` in
     one incident and a directory two levels below it forty minutes later, because the user edited
     the list in between. The record cannot be grouped by rule across time, and
     `usewarden allow scope.forbidden_paths[12]` waives whichever entry has drifted into slot 12.
2. **`commands.deny[0] (rm-rf-outside-repo)` — 9 unwanted, 0 wanted.** Most-fired command rule in
   the window and it has never once been right here. Three of the nine involved no deletion at all.
   This is the same class D-250 measured and D-259 narrowed; D-259 fixed the Python-heredoc shape,
   and the shapes that survive it are the shell heredoc (`cat > file <<'EOF'`) and the quoted
   argument (`grep 'rm -rf'`) — the latter documented as open.
3. **`scope.allowed_paths` — 3 unwanted, 0 wanted.** The escape hatch and the scratchpad. Both are
   places the user did not choose and cannot reasonably be asked to enumerate.

Everything else — `drop-table`, `dotenv-access` — is a single instance each and is the same
text-versus-command class as (2).

## 7. Would the Phase 2 labelling criterion have caught these before they shipped?

**No. It would have caught one of the thirty-two, and it is blind to the class that caused the
churn by construction rather than by accident.**

The criterion is implemented in `scripts/classify-incidents.mjs`. It strips heredoc bodies and
quoted literals from a stored command, re-runs the rule's own pattern over what is left, and
sorts the result into three labels. Its own header states the third one:

> `FILE-TOOL` — no command at all: a Read/Write/Edit event carrying a path. **There is no
> text/command ambiguity to resolve, so these are real by construction.**

Run over exactly the forty blocks in this window:

| Label the criterion assigns | n |
|---|---|
| `FILE-TOOL` — *labelled a true positive without examination* | **28** |
| `FIRED-ON-COMMAND` / UNREPLAYABLE | 6 |
| `FIRED-ON-TEXT` / UNREPLAYABLE | 5 |
| `FIRED-ON-TEXT` / still fires today | **1** |

Three things follow, and none of them is a criticism of the criterion doing its own job well.

**It cannot see a path false positive at all.** 28 of the 40 blocks — and 21 of the 32 unwanted
ones — are file-tool events. "Real by construction" is a sound assumption for the question the
criterion was built to answer, which is *did the shell actually invoke this*. It is exactly wrong
for the question this window raises, which is *should this path have been on the list*. Every
Class A, B and E block would be labelled a true positive and closed.

**Of the twelve it can see, eleven are unreplayable** — the storage defect of D-258: `attempted`
holds a truncated display rendering, not the command, so the heredoc terminator is missing and no
parser can judge it. Per §4.4 those are counted against the total and never as a pass. The
criterion returns an actual verdict on **one** of the forty.

**And it could not have run before shipping in any case.** It consumes a record of real firings.
0.1.0 shipped before this record existed. The only pre-ship substitute is a fixture, and a fixture
cannot produce this class: the author of a scope fixture picks a path that *should* be blocked, so
the fixture agrees with the rule by construction — the same trap D-243 named, where a unit test
passed because its fixture already had the shape the bug removed.

**The conclusion is not that labelling should be skipped.** It is that the labelling phase needs a
second criterion it does not currently have, for path blocks, and that criterion cannot be a
replay. The only signal that separates a wanted path block from an unwanted one is whether the
target was inside the work the session had been told to do — which is information the record
already holds, in `sessions.goal` and in `cwd`, and which nothing currently reads for this purpose.
Naming that is the whole output of this document.

- **No rule is changed.** The ordering from the previous plan stands: label, then tune.
- **No default is changed.** The scope question is a published-behaviour change and is a

- **Nothing is reinstalled.** Protection stays off on the author's machine until he says otherwise.

# THE VERDICT — 2026-09-08

> This document was written to *diagnose* the churn and to *recommend* whether usewarden's default
> should be project-scoped rather than machine-wide. The recommendation was deferred twice because
> the record could not be replayed and the answer would have been an opinion. It can now be
> replayed, and every number below is `usewarden replay` against the frozen 92-block label set with
> everything except the scope shape held fixed.

## The recommendation, in one line

**Make `allowed_paths` session-derived. Leave `forbidden_paths` machine-wide. Do not make the
default "project-scoped" — that is one change, and it is really two, and they want opposite
answers.**

## The measurement

| scope shape | precision | coverage | false positives |
|---|---|---|---|
| **as recorded** — what the founder actually lived through | 54.3% (50/92) | 100% (50/50) | 42 |
| today's shape: enumerated absolute `allowed_paths`, machine-wide `forbidden_paths` | 90.9% (50/55) | 100% (50/50) | 5 |
| **recommended**: session-derived `allowed_paths`, machine-wide `forbidden_paths` | **94.3% (50/53)** | **100% (50/50)** | 3 |
| project-scoped BOTH halves — the intuitive symmetric move | 90.3% (28/31) | **56% (28/50)** | 3 |

## The trade-off, stated plainly

**Project-scoping `forbidden_paths` costs 22 of the 50 real catches to remove 2 false positives.**
Eleven real catches sacrificed per annoyance removed. And they are not 22 arbitrary catches — 21 of
them are reads and writes into directories the operator had declared off-limits, from sessions
running in a *different* repository. That includes every read of the private journal under
`~/Documents`, which is the single clearest piece of value in the whole record and the thing a
project-scoped tool is structurally unable to see: a hook that only knows about the repository it
was invoked in cannot notice the agent leaving it.

Precision does not even improve. 90.3% against 90.9% — the two false positives it removes are
almost exactly offset by the true positives it removes from the denominator. **The narrow scope buys
nothing and costs 44% of the coverage.**

## Why the annoyance pointed at the wrong culprit

The churn was real: 32 of 40 blocks in 72 hours were unwanted, and the tool was uninstalled over it.
The natural inference — "it is watching too much, so make it watch less" — is wrong, and the
labelled corpus says why.

Of the 42 false positives in the 92 stored blocks, **35 were the engine misreading shell text**: a
markdown backtick inside a here-document read as command substitution, a `.sh` filename read as a
shell, a phrase inside `grep -n '...'` read as a command. Those have nothing to do with scope. They
were fixed at the rule level (D-279) and precision went 63.3% → 86.2% without the scope moving at
all.

Only **3** of the 42 were about scope in the sense this document was asking about, and all three
were the *other* half: the agent refused access to its own scratchpad, and a delete inside the
project the session was actually working in.

**So the diagnosis in the body of this document — that `scope:` ships both halves with the same
default and that this is the defect (D-264) — was right, and the fix it implies is narrower than
"go project-scoped".** Enforcement is machine-wide because the hooks are registered at the user
layer. Permission was one directory: whichever one `init` happened to be run in, frozen into the
global policy. Every other project on the machine was out of scope for writes from the moment of
install, including projects that did not exist yet — and the only way for a user to say "do not
wander" was to enumerate their other projects into `forbidden_paths`, a list that is right the day
it is written and wrong the first day they work in one of them.

## What was implemented

`defaultPolicy` now writes `allowed_paths: ['.']`, which resolves against the event's own repository
root — or its cwd, when there is no repository — on every event. This is the model Codex CLI's
`workspace-write` already uses, and it is what D-264 recommended on 2026-08-29 from primary sources.

**What it does not lose.** Writing from repository A into repository B is still outside A's tree, so
the sibling-repo catch is intact and the sabotage suite asserts it. `forbidden_paths` is untouched
and still absolute.

**What existing users get.** Nothing, until they regenerate their policy: a `usewarden.yaml` written
by an earlier `init` carries absolute paths and keeps them. That is deliberate — silently rewriting
a user's policy file is not a scope fix, it is a different problem. The 90.9% row above is what the
founder's current file would give with today's engine; the 94.3% row is what a fresh install gives.
