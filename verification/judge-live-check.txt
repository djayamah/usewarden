---------------------------------------------------------------------------
THE EARLIER FAILURE, AND WHAT IT CHANGED
---------------------------------------------------------------------------
The first attempt on 2026-08-20 failed with a bare HTTP 401 against a 106-character credential - a
doubled paste. Diagnosing it meant ruling out the auth header, the API version and the model id
one at a time, when the answer was visible in the value's shape the whole time. Two fixes came
out of that, both covered by tests:

1. usewarden now inspects the credential's SHAPE before the call and attaches what it saw to any
   auth failure. The same doubled value now reports, in one line:

     JUDGE_KEY_SHAPE: the gemini credential is 106 characters and its first half is identical
     to its second - it looks like the same key pasted TWICE. Re-enter it once.

   It classifies doubled, truncated, wrong-provider, whitespace-contaminated and unrecognised
   shapes, using only length and prefix class. It never reads, stores or prints the value, and it
   never REFUSES the call - Google changed the key format without publishing a spec, and a check
   that rejected an unrecognised shape would have locked out every new user that week.

2. A LAUNCH-BLOCKING credential-leak bug was found while auditing for the new format. See below.

---------------------------------------------------------------------------
LAUNCH-BLOCKING BUG FOUND AND FIXED: AQ.-format keys were never redacted
---------------------------------------------------------------------------
Google now issues Gemini keys as 'AQ.' + ~50 characters (53 total). usewarden's redactor knew
only the legacy 'AIza' + 35 format (39 total). Four controls were therefore blind to a live key
belonging to anyone who signed up recently:

  src/util.ts redact()          -> incident rows, log lines, and JUDGE PAYLOADS sent to a third
                                   party carried the key verbatim
  scripts/pre-public-scan.sh    -> the publication gate would have passed a repository with a
                                   leaked new-format Google key in its history
  scripts/judge-live.sh scrub() -> the key could have reached a terminal transcript
  service/src/validate.ts       -> the aggregator's content gate would not have caught one

All four now handle both formats. redact() additionally strips the EXACT configured key value by
identity, which needs no knowledge of any format and would have caught this with no pattern at
all - because a prefix list is a guess with a shelf life, and this is the second time that has
been proved in this repository (see D-081).
