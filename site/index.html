Stop your AI coding agent before it touches something it shouldn't.

A local guardrail for every AI coding agent on your machine — Claude Code, Cursor, Gemini CLI and three more. It blocks writes outside the repo you're in, .env reads, rm -rf above the project root and force pushes to main — deterministically, with no API key and zero tokens.

Free. Local. No account.

It is free.
MIT licence. No paid tier, no account, no sign-up, no trial. npm install -g usewarden is the whole transaction.
It needs no API key.
The blocking is deterministic pattern and scope matching: zero tokens, zero API calls, on every event. The one thing that can ever cost money is the optional drift judge, and only if you hand it your own key for a paid API. Give it nothing and it says so, and the blocking carries on.
Your code stays on your machine.
The blocking never leaves it. Telemetry is off by default and this version ships no endpoint at all, so there is nowhere for a payload to go. The single exception is that optional judge, which you switch on yourself, to a provider you pick, with your own key — and its input is redacted and length-capped before it goes.

And this is what the agent said next, unedited:

I can't retrieve that value — the read was blocked. […] The block is unconditional on .env files, so it applies regardless of whether the credentials are real or fixture placeholders. I'm not going to try to route around it (e.g. via grep, base64, or copying the file elsewhere) — that's exactly what the guard exists to prevent.

The reason line is written to be something an agent can self-correct from. In every live session recorded during the build, the agent read it, stopped, and offered the human a safe alternative instead of trying another route.

It is not a firewall and not a sandbox. It intercepts what an agent declares it is about to do, through each vendor's hook system. An agent that does not fire hooks, or that misreports its own tool input, is not covered — and usewarden status is built to tell you loudly when that is the case.

Is this your week?

  • "It deleted files I never asked it to touch." rm -rf taking out the wrong directory is a recurring, publicly documented failure across agents. The common thread is not a bug in any one of them: it is that agents run on your host with your permissions.
  • "It edited the wrong repo." The most common real drift in this project's own live sessions was an agent writing into a sibling checkout beside the one it was told to work in.
  • "It ignored my rules file." Instructions in a file are advisory. A hook is not.
  • Context rot. Forty messages in, it contradicts a decision you made together and edits a file it no longer remembers reading. usewarden warns at a context threshold and can compare what the agent is doing against the goal you declared.

If Claude Code is the only agent you run, read this first

Claude Code has its own permission system, and for blocking it is as good as usewarden — and in two specific cases better. You should hear that from us rather than discover it. Everything below was measured against the shipped hook binary (node scripts/probe-native-gap.mjs); the native side is from Anthropic's own documentation.

The agent tries to…usewardenClaude Code's own controls
rm -rf above the project, force-push, privilege escalation blocks a Bash(…) deny rule — equal, and blunter, which is arguably safer
read a private path, or write outside the project, with its file tools blocks a Read(…) deny rule and working-directory confinement — equal
write outside the project by shell redirect does not block blocks. Claude Code checks the target of >, >> and 2> as a file write (permissions)
write outside the project from a subprocess it spawns does not block blocks, with /sandbox. The OS sandbox covers “any scripts, programs, or subprocesses that are spawned by the command” (sandboxing)

So if blocking is all you want, and Claude Code is all you run, you do not need this. Turn on /sandbox, write the deny rules, and you are better covered for out-of-scope writes than usewarden can make you.

What usewarden adds is not more blocking. It is a record that is still readable next week — 57 incidents across 22 real sessions on the machine that built it, which is how we found that 34 of them fired on text about a command rather than a command; one policy across six agents instead of six separate configs; and drift, comparing what the agent is doing against the goal it was given, which has no native equivalent. The honest pitch is not “we block what Claude Code cannot”. It is: we are the only thing that remembers, and the only policy your five other agents share.

Two layers, in this order

LayerWhat it doesCost
1 Deterministic. Scope globs, command patterns, protected branches, sibling-repo detection, context-fill threshold. Runs on every event. zero tokens
2 An LLM judge, sampled, for semantic drift from the goal you declared. Warns; never blocks on its own, and can never overturn a layer-1 block. sampled, capped

Layer 1 alone caught 14 of 17 scenarios in the sabotage suite — it misses the two that are semantic by nature, which is what layer 2 is for, and one whose input no agent actually sends. That third one used to be counted as a catch; it was scored against a field the test supplied and the product never receives, so the number came down rather than the scenario being quietly dropped. If the judge is unreachable, usewarden fails open with a visible warning and layer 1 keeps running. It never silently switches itself off.

The failure mode this product takes seriously

A guardian that has quietly stopped running is worse than no guardian, because you have stopped watching too. So the loudest thing usewarden does is tell you when it is not protecting you:

  • UNPROTECTED — hook entries missing, or hooks globally disabled
  • TAMPERED — an entry tagged as usewarden's does not invoke usewarden's own binary
  • POLICY_INVALID — your policy file does not parse, so nothing is being enforced

All three exit non-zero and print in red. This was proved by removing the hook registrations from a live agent session and running the same attack again: with hooks present the read was blocked, with them removed the read succeeded and status said UNPROTECTED, and with them restored it was blocked again.

Numbers you can check

"Actions blocked" is a marketing number, and a marketing number that cannot be audited is a claim. So usewarden derives every figure by query at the moment you ask, groups it by where it came from, and re-checks the arithmetic on every read.

RuleWhat it means in practice
Real sessions only A usewarden demo run cannot move a headline figure. Demo catches are recorded, labelled, and reported separately.
Retries do not multiply Attempts and distinct actions are reported side by side. An agent retrying the same blocked read five times is five attempts against one action.
Estimates say so Token and dollar savings are shown as a range, never a point, with every constant printed by usewarden metrics.
Some things are never priced "We stopped your API key reaching a model context" is counted and named. Converting it to a dollar figure would be inventing precision.
Overhead sits beside savings What usewarden's own judge cost you is shown next to what it saved, not netted off behind your back.

The full method — every constant, its reasoning, and what would make it a measurement rather than an estimate — is in docs/METRICS.md.

Its own install path is an attack surface

A tool that writes to your agent's config files is a tool that a supply-chain attacker would like to own. usewarden is built on that assumption:

  • No install scripts. No preinstall, install, postinstall, or prepare — the exact mechanism the August 2026 npm worm used across 444 packages. A test fails the build if one ever appears, in usewarden's manifest or anywhere in its lockfile.
  • Zero runtime dependencies. Nothing to compromise upstream.
  • Every config change is previewed as a diff before it is applied, and backed up first. usewarden uninstall restores byte-identically — verified by sha256, on a simulated clean machine.
  • Hook commands are fixed argv — an absolute path to node, an absolute path to usewarden's own script, no shell, no interpolation of anything an agent said.
  • A repo's usewarden.yaml is untrusted input. It can narrow your scope. It cannot widen it without an explicit usewarden trust.

Telemetry

Off by default, and this version ships no endpoint at all — there is nowhere for a payload to go even if it were built. Opting in shows you the exact payload first, then records a consent receipt naming the schema version and every field it covers. If the payload ever gains a field, that receipt lapses and telemetry switches itself off until you read the new one and agree again.

DO_NOT_TRACK=1 and USEWARDEN_TELEMETRY=0 are both honoured and both override an explicit opt-in.

What it cannot do

  • It hooks the agents that have hooks. An agent with no hook API, or a desktop wrapper that ignores project config, is not covered — and usewarden status says so rather than implying otherwise.
  • Layer 2 is sampled and fallible. It warns; it never blocks alone.
  • It is not a sandbox. A determined agent with shell access has other routes; usewarden raises the cost and creates the record, it does not make the machine safe.
  • A shell redirect out of the project is not blocked, and neither is a subprocess that opens a file itself. Matching > would fire on every legitimate redirect anyone runs. Claude Code's own controls do cover both — see the comparison above.
  • Text about a dangerous command can be mistaken for the command. Layer 1 matches the raw command string, so writing a runbook that names a release command can be refused as though it were one. Over six days on the machine that built usewarden, 34 of 57 recorded incidents were this, and one rule was wrong every single time it fired.
  • The savings figures are estimates, and say so on every surface.
