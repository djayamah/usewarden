Your agent hook says it is registered. It has never run.

usewarden write-ups · piece 1

The symptom: you added a hook to ~/.claude/settings.json. The JSON is valid. The agent starts fine. Nothing in the output mentions hooks at all. You assume it is working, because there is nothing to suggest otherwise.

It has never executed once.

What was actually happening

The hook was registered like this:

{ "type": "command", "command": "/abs/path/to/dist/src/cli.js", "args": ["hook", "claude", "pre_tool"] }

That is a real, existing, readable file. It has a shebang. The path is correct. And every single invocation failed with:

EACCES: permission denied, posix_spawn '/abs/path/to/dist/src/cli.js'

The build compiled TypeScript to dist/, and tsc does not preserve or set an execute bit. The file was rw-r--r--. To run it as a command you need rwxr-xr-x. The agent tried to spawn it as a process, the OS refused, and the hook failed.

What made it invisible was what the agent did with that failure. A hook that cannot be spawned is not a deny — it is an error. The agent's own behaviour on a hook error is to carry on. So the tool ran, the file got written, the command got executed, and the only trace was a line in a log nobody was reading.

Meanwhile the tool's own status command said PROTECTED, in green, correctly, by its own logic: it checked that the hook entries were present in the config file, that they were tagged as its own, and that the config parsed. All three were true. None of them is the same question as did this ever run.

How it was found

Not by a test. By running a real agent session and reading the transcript.

The test suite at the time was green, and it was green for a good reason: every test called the hook handler as a function. Functions do not need an execute bit. The suite proved the logic was right and could not have proved the file was reachable, because it never went through the path — spawn a process from a config file — where the failure lives.

The first real session against a real agent failed on every event. It took about ninety seconds to find once anyone looked, and it had been sitting there through a fully green suite.

What changed

Three things, and only one of them is the obvious one.

1. Name the interpreter explicitly. The registration is now:

{ "command": "/abs/path/to/node", "args": ["/abs/path/to/cli.js", "hook", "claude", "pre_tool"] }

Node is the executable; the script is an argument. That removes three separate failure modes at once — the execute bit, a wrong or missing shebang, and Windows, which has no shebang mechanism at all. Both components stay absolute paths, which matters for a different reason: a hook command that resolves through PATH can be hijacked by anything that puts itself earlier on PATH.

2. A check that the interpreter itself is real. Naming the interpreter introduces a new way to break: the recorded node path goes stale if you replace your node install. So there is now a diagnostic that asserts the node binary exists and is executable, separately from asserting that the script exists — two checks, because they fail for different reasons and have different fixes.

3. The status command stopped being allowed to infer. "The config contains my entries" is not evidence that anything ran. It is now one of several separately-reported facts, and the state that matters — has this fired — is answered by whether events were actually recorded, not by reading the config back.

The general shape

This is worth naming, because it is not really about execute bits.

A guardrail that fails open and reports on itself will report success. Every component here was behaving correctly and locally: tsc does not set execute bits, the agent continues past a hook error rather than hard-failing your session, and a status check that reads a config file correctly reports what is in the config file. The failure is in the gap between them, and no component can see the gap.

The test suite could not catch it because the suite tested the unit and the failure was in the integration with the operating system. Green tests were not wrong; they were answering a different question than the one anyone was actually asking.

If you have a hook, a git hook, a pre-commit, a CI guard, or any other thing whose job is to intervene: the check you want is not "is it configured". It is "how many times has it run, and when was the last one." If the answer is zero and you expected thousands, you have this bug. If your tool cannot tell you that number, that is the first thing to build.
